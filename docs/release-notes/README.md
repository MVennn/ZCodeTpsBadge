# release-notes/

> **一句话**：面向用户的 Release 说明，一个版本一篇，文件名 = `X.Y.Z.md`；
> 写成清单（一行一条），不写成文章。

发版时直接拿它当 GitHub Release 正文：

```bash
gh release create vX.Y.Z --title "vX.Y.Z" \
  --notes-file docs/release-notes/X.Y.Z.md
```

## 为什么要单独放一份

`CHANGELOG.md` 是**开发者记录**：症状 / 根因 / 改法 / 验证结果 / 构建细节。
Release 说明是**给用户看的**：短、清单、只讲「我现在能拿到什么」。
两者受众不同，不能一份两用（见 [RELEASE.md](../RELEASE.md) §1.1）。

## 形状

**清单，不是文章。** 开头一句加粗说清这版是什么，`## 本版内容` 下按对象分区、
一行一条，最后是固定尾巴。

```markdown
**挂后台再回来，统计卡的平均 / 最高 / 最低不再被稀释。**

遇到问题、想要新功能，到 [Issues](https://github.com/MVennn/ZCodeTpsBadge/issues/new/choose) 反馈。

## 本版内容

**统计卡**

- 修复 平均速度 —— 悬停统计卡；窗口挂在后台再回到前台，平均不再掉到个位数。

**补丁**

- 调整 补丁内容 —— 需重新运行 `tools/apply.cmd`；本次补丁内容有变，旧补丁不会自动更新。

---

需要 Windows + ZCode 桌面版；补丁会修改本地 `app.asar`，ZCode 升级后需重新运行
`tools/apply.cmd`。安装步骤见 [README](https://github.com/MVennn/ZCodeTpsBadge#安装)。

---

> 风险提示：本项目非官方，与 ZCode 官方无隶属、合作或授权关系；补丁会修改本地
> ZCode 安装目录的 `app.asar`，ZCode 升级会覆盖补丁、需要重新应用；徽标数值取自
> ZCode 内部调试快照里的模型 usage，不用于计费或性能结论。
```

结尾两段是**固定尾巴**，每版照抄不动（风险提示属法律留痕：持续提示、提示在先），
不算重复内容。0.3.0 起数据源从字符估算改为 `session/debug`，风险提示同步改口径；
更早的版本保留当时的估算措辞，不回改历史。

## 反馈入口：写在开头，链接必须是绝对地址

第一行是加粗总结；**紧接的第二行是反馈入口**，一行、不是清单条目，然后才是
`## 本版内容`：

- 链接只用绝对地址
  `https://github.com/MVennn/ZCodeTpsBadge/issues/new/choose`，不用相对链接；
- `issues/new/choose` 会先让用户选「问题反馈」还是「功能建议」，两类都收；
- 已发布的历史正文不回填；新增版本按这个形状写。

### 一条怎么写

```
新增 / 调整 / 修复 / 优化 / 移除 + 功能名 —— 入口；一句话
```

- **动词只有五个**：新增（以前没有）、调整（行为、默认值、位置变了）、
  修复（以前不对，**含底层与实现层**）、优化（用户能感知的更快 / 更小 / 更顺）、
  移除（删功能）。都写全称 —— 单字「修」读着不像词。
- **功能名照抄界面**：徽标、悬停统计卡、统计卡上的「本轮速度 / 输出 / 思考 /
  输入 / 缓存命中 / 生成耗时 / 会话请求 / 平均命中 / 状态」、`tools/apply.cmd`。
- **入口**写用户点得到的位置：「输入框底部工具条」「悬停徽标」「`tools/apply.cmd`」；
  不需要找入口的（装上就看得见），改写场景（「徽标」「悬停统计卡」）。
- **功能**一句说完，写用户拿到什么。不写怎么用、不写为什么、不写实现。
- 说人话。「rAF」「MessagePort」「增量摊还」这类只对开发者有意义的词别写；
  真要交代限制，写用户看得见的后果（「参数很长时数值会偏高」）。
- 一行一条。两句才说得清 → 拆成两条，或者这条本来就该留在 CHANGELOG。

## 底层与内部改动：算「修复」，写后果不写根因

用户看不出区别、但代码确实改了的改动（竞态、时序、重连、重构、删死代码）
**也算本版内容**：

| 改了什么 | 动词 | 一行怎么写 |
|---|---|---|
| 底层缺陷（竞态、泄漏、越界、时序） | 修复 | 写「以前会怎样」的用户可见后果，不写根因 |
| 重构 / 拆文件 / 收敛依赖（行为零变更） | 修复 | `修复 代码拆分 —— 哪几处拆开，行为零变更` |
| 删死代码、清无用资源 | 修复 | `修复 死代码 —— 删了哪几处，行为零变更` |
| 用户能感知的更快 / 更小 / 更顺 | 优化 | 写「快在哪」，能给数字就给 |

一句话记法：**凡是在 `git diff` 里出现过、且用户可能感知的东西，说明里都要有一行。**
写不长不是本事，漏了才是问题 —— 篇幅红线排在覆盖率之后。

## 覆盖率红线

**本版全部用户可感知改动必须进说明**，一条不漏：

- 修复 → 写用户可见的后果，不写根因长文；
- 性能 / 内部整理 → 并进「优化」或「修复」，按对象拆行；
- 文档 / 仓库结构 → 并进「调整 仓库」，用户不可见的也照写；
- 写完拿 CHANGELOG 对应段落逐条对：CHANGELOG 里的每一处用户可感知改动，
  说明里都得能找到对应行。

## 篇幅

- 覆盖率优先于篇幅：先保证一条不漏，再谈合并。
- 分组按对象走（徽标 / 悬停统计卡 / 补丁 / 修复 / 优化），不按轻重排。
- 合并手法：同一对象的界面打磨并成一行；性能同类项归并成一行但要列出对象。

## 别写这些

| 别写 | 为什么 |
|---|---|
| 第二人称叙述（「点一下就…」「你可以在…里改」） | 用户要的是有什么，不是操作步骤；步骤归 README |
| 「原来是这样，所以现在…」的原因与取舍 | 解释属于 CHANGELOG |
| 实现原理、RPC 格式、字段来源 | 同上 |
| 开关默认值、改完要不要重启 | 通用信息，不随版本变（固定尾巴统一说） |
| 「之前是什么样」的对比 | 只有修复条目允许一句症状，其余不写 |
| 凑数的「注意」区块 | 每版都一样的提醒写进固定尾巴，不逐版重复 |

## 改已经发出去的说明

已发布的 Release 走「更新说明」，不要删了重建、更不要移动 tag：

```bash
gh release edit vX.Y.Z --notes-file docs/release-notes/X.Y.Z.md
```

改完用 `gh release view vX.Y.Z` 核对线上正文与文件一致。
