# 版本命名规范

> **一句话**：有没有「功能更新」决定动哪一位 —— 有功能进次版本（+0.1.0），
> 没有就进补丁版本（+0.0.1）。

---

## 1. 三段式与进位

版本号写在 `package.json` 的 `version`，格式 `主版本.次版本.补丁版本`。

| 这次包含…… | 动哪位 | 例子 |
|---|---|---|
| 没有功能更新：修 bug、调样式 / 文案 / 文档、改脚本 | 补丁 +0.0.1 | `0.1.0` → `0.1.1` |
| 有功能更新：新增功能、现有行为 / 交互变化、移除功能 | 次版本 +0.1.0，补丁归零 | `0.1.1` → `0.2.0` |
| 不兼容变更：配置格式不兼容、最低 Node 版本提高等 | 主版本 +1.0.0，后两段归零 | `0.2.0` → `1.0.0` |

进位是连锁的：次版本进位时补丁必然归零。

## 2. 怎么判断「有没有功能更新」

- 用户能找到一个以前没有的东西（新入口、新交互、新显示项），
  或现有功能行为变了 → `+0.1.0`；
- 只是「做得对不对」（修复）或「长得好不好」（样式 / 文案 / 间距）→ `+0.0.1`。

边界：

| 情况 | 算不算功能更新 |
|---|---|
| 修「徽标不显示」 | 否，`+0.0.1` |
| 徽标从右下角移到工具条 | 是，`+0.1.0`（位置是用户可感知的行为变化） |
| 新增悬停统计卡 | 是，`+0.1.0` |
| 只改图标 / README / 文档 | 否，`+0.0.1` |

## 3. tag 与 Release

- tag 格式：`vX.Y.Z`（如 `v0.1.0`）；
- tag 与 `package.json` 的 `version` 必须一致；
- Release 说明写在 `docs/release-notes/<version>.md`；
- 发版流程见 [RELEASE.md](RELEASE.md)。

## 4. 落地位置

发版前改两处：

```json
// package.json
"version": "0.1.0"
```

```markdown
<!-- docs/release-notes/0.1.0.md -->
# 0.1.0 — 2026-10-21
```

`CHANGELOG.md` 的 `[未发布]` 段在发版时改为 `[0.1.0] — YYYY-MM-DD`。
